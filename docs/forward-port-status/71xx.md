# 71.86.15 → modern kernel — forward-port status

**Status: build-verified on 2 of 4 target kernels.** `nvidia.ko` compiles
clean (zero errors) via `patches/71xx/kernel/0001`-`0003` on:
- Ubuntu 20.04/kernel 5.4.0-200-generic (amd64)
- Ubuntu 24.04/kernel 6.8.0-139-generic (amd64)

**Not yet attempted:**
- Debian trixie/kernel 6.12 (amd64) — the actual `kernel_max` target
- Debian bookworm/kernel 6.1 (**i386**)

Both 96xx and 173xx needed a separate `kernel/0004` to close exactly these
two gaps (a Debian split-kernel-headers incompatibility and a GCC 14
default-warning promotion breaking conftest.sh's probes). 71xx shares the
same conftest.sh/Makefile.kbuild lineage as 96xx, so the same two issues are
almost certainly here too, but this has not been ported or tested yet.

Not runtime-tested on real hardware.

**Reference:** 96xx's own forward-port (`docs/forward-port-status/96xx.md`,
`patches/96xx/PROVENANCE.toml`) was the direct template — most of `kernel/0003`
here was produced by fuzzy-patching 96xx's already-verified `kernel/0003` onto
71xx's tree and manually fixing the rejects, not written from scratch. 71xx is
a full major version older than 96xx and lacks `nv-i2c.c` entirely (no I2C bus
support in this driver at all).

## API breaks found and fixed (kernel/0003)

Full detail, including *why* each fix is shaped the way it is, lives in
`patches/71xx/PROVENANCE.toml`'s entry for
`kernel/0003-modern-kernel-forward-port.patch`. Most of the fix set is
identical to 96xx's own `kernel/0003` (see `docs/forward-port-status/96xx.md`
for the full list — ACPI headers, arch/x86-local header probes,
`arch_phys_wc_add`, `smp_call_function`/`on_each_cpu` int→void,
`spin_unlock_wait`, CPU-hotplug notifier removal, `ioremap_nocache`,
`vm_flags_set`, the full procfs shim, `init_timer`/`timer_setup`, the CR4 asm
bug, `__flush_tlb()`, `CORE_OBJS`/`if_changed`, `tasklet_disable()`'s
internal GPL-only symbol). 71xx-specific issues found on top of that:

- **`pm_message_t` conftest probe self-sabotage**: the probe's own test source unconditionally `#include`d `<asm/system.h>` (removed from the kernel long ago), making the probe hard-fail its own compile regardless of whether `pm_message_t` is actually present — always reporting "absent" and making nv-linux.h's compat `typedef u32 pm_message_t` fallback collide with the kernel's real struct-based `pm_message_t`. Fixed by dropping the stray include.
- **conftest.sh's own internal architecture gaps** (three compounding issues, found while trying to make the ported `set_pages_uc` fix actually take effect): `CONFTEST_PREAMBLE` never included `conftest.h`/`autoconf.h` (unlike 96xx/173xx), so no probe could see another probe's result; fixing that exposed that 71xx's `compile_tests` case computes its `NV_GENERATED_AUTOCONF_H_PRESENT` define *after* running the probes rather than before, breaking every single probe uniformly once the preamble started referencing it; fixing *that* exposed that `select_makefile` (and the framebuffer-conflict sanity checks) run before Kbuild's own `conftest.h` generation and, once they started needing `conftest.h` too, left a stale one behind that made Make's prerequisite-less `$(obj)/conftest.h:` rule treat the file as already up to date and never regenerate it for the real build at all. All three fixed; see PROVENANCE.toml for the exact detail on each.
- **`_get_phys_address()`'s user-address path always took the dead manual pud/pmd/pte walk**, regardless of whether `set_pages_uc()` (the modern fast path) was detected present — unlike 173xx's version, which gates its *entire* function body (both kernel- and user-address cases) behind one `#if defined(NV_SET_PAGES_UC_PRESENT))`. Restructured to match 173xx's simpler all-or-nothing gating, which also sidesteps two additional problems only reachable through that same dead path: the `pud_offset()` 4/5-level-pagetable signature drift, and `pte_offset_map()`'s RCU-based reimplementation on 6.5+ kernels pulling in the GPL-only `__rcu_read_unlock` symbol at link time.
- **`mm->mmap_sem` renamed to the `mmap_lock` API in Linux 5.8** → `NV_MMAP_READ_LOCK`/`NV_MMAP_READ_UNLOCK`, gated on `LINUX_VERSION_CODE`.

## Known gaps

- Debian trixie (6.12, the actual `kernel_max` target) and i386 (Debian
  bookworm, 6.1) not attempted at all yet — no Debian-split-headers or gcc14
  fix has been ported to 71xx's conftest.sh.
- No runtime testing on real hardware (NV0x/NV1x TNT/TNT2/GeForce 256/GeForce
  2/4 MX).
