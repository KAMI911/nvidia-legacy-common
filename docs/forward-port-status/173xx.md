# 173.14.39 → modern kernel — forward-port roadmap

**Target:** compile-clean against Linux 6.12 LTS (amd64 + i386), runtime-validated
later on real GeForce FX hardware.
**Reference:** `patches/304xx/` — 304.137 shares the pre-modular layout
(`usr/src/nv/{nv.c,nv-linux.h,os-interface.c,nv.h,nv-vm.c,os-agp.c}`) and has a
maintained patch set to 7.0. Most 304 patches port to 173 with line-offset and
context fixups; 173 lacks `nv-drm.c`, `nv-mmap.c`, `nv-mlock.c`, `nv-procfs.c`,
`nv-pat.c`, so DRM/PAT/mmap patches are dropped and a few things live in `nv.c`
that 304 moved out.

## The one genuine blocker: `spin_unlock_wait()` (4.14)

173's RM lock code (`nv.c`, around `nv_lock_init`/the `nvl->rm_lock` spin section)
calls `spin_unlock_wait()`, removed in Linux 4.14 (torvalds/linux 952111d7db02
"locking: Remove spin_unlock_wait() generic definitions"). 304 does **not** hit
this — its lock code was already reworked upstream. Options for 173:

1. Replace `spin_unlock_wait(l)` with `spin_lock(l); spin_unlock(l);` — correct
   *only if* the surrounding code does not rely on not taking the lock (needs a
   read of the RM lock protocol — the call sites acquire-then-wait for drain).
2. Backport 304's newer lock handling for that region.

This needs a careful read + FX hardware to prove no deadlock/corruption. Until
then 173 `kernel_max` stays a **target**, not a claim.
