# 173.14.39 → modern kernel — forward-port status

**Status: build-verified.** `nvidia.ko` compiles clean (zero warnings) via
`patches/173xx/kernel/0001`-`0004` on:
- Ubuntu 20.04/kernel 5.4.0-200-generic (amd64)
- Ubuntu 24.04/kernel 6.8.0-139-generic (amd64)
- Debian trixie/kernel 6.12.107 (amd64, gcc 14.2.0) — the actual `kernel_max` target
- Debian bookworm/kernel 6.1.0-53-686-pae (**i386**)

`kernel/0004` closed the two gaps noted below as of `kernel/0003`: it fixed a
Debian split-kernel-headers-package incompatibility and a GCC 14 default-warning
promotion that broke essentially all of `kernel/0003`'s conftest.sh probes on
Debian/gcc-14 — a real, previously-unknown gap that affected every currently-
shipped 173xx target on Debian 12/13 or any gcc-14+ toolchain, discovered while
specifically trying to close the "6.9-6.12 untested" gap. See
`patches/173xx/PROVENANCE.toml`'s `kernel/0004` entry for the full detail. Not
yet runtime-tested on real GeForce FX hardware.

**Target:** compile-clean against Linux 6.12 LTS (amd64 + i386), runtime-validated
later on real GeForce FX hardware.
**Reference:** `patches/304xx/` — 304.137 shares the pre-modular layout
(`usr/src/nv/{nv.c,nv-linux.h,os-interface.c,nv.h,nv-vm.c,os-agp.c}`) and has a
maintained patch set to 7.0. Most 304 patches port to 173 with line-offset and
context fixups; 173 lacks `nv-drm.c`, `nv-mmap.c`, `nv-mlock.c`, `nv-procfs.c`,
`nv-pat.c`, so DRM/PAT/mmap patches are dropped and a few things live in `nv.c`
that 304 moved out.

## API breaks actually found and fixed (kernel/0003)

The table below was this doc's original *predicted* break list, written before
any of 173xx actually reached real compilation (that needed the separate
`kernel/0001` kbuild `M=` fix first). Once compilation was genuinely
unblocked, the real break list turned out to differ from the prediction in
specifics (found empirically, one `docker run` iteration at a time, against
real Ubuntu 20.04/5.4 and Ubuntu 24.04/6.8 headers) even though the general
shape — ACPI, timers, procfs, vm_flags, MTRR, tasklet/GPL symbols — rhymes
with the predictions below. The prediction table is kept for reference; treat
it as historical, not current. The actual fix list, with full detail
including *why* each conftest probe is written the way it is, lives in
`patches/173xx/PROVENANCE.toml`'s entry for `kernel/0003-modern-kernel-forward-port.patch`.

Notably, `spin_unlock_wait()` (flagged below as "the one genuine blocker,
hard, needs care") turned out to be no harder than the other API removals in
practice: this driver's one call site is a plain "wait for the lock to be
free" wait, not a partial-lock protocol, and the fix (`spin_lock(l);
spin_unlock(l);`) mirrors exactly what upstream Linux itself did at every
other in-tree caller when the function was removed. That said, this was
reasoned from reading the call site and from Linux's own removal precedent,
not from testing on real hardware under contention — see "Known gaps" below.

## Known gaps

- **No runtime testing.** Everything above is compile- and link-verified only
  (`nvidia.ko` produced, zero warnings, on 5.4, 6.8, 6.12, and i386 6.1).
  Nobody has loaded this module on real GeForce FX hardware. The
  `spin_unlock_wait()` removal in particular (see above) is reasoned to be
  safe, not proven safe under load.
- **ACPI display-switch handle detection (CRT/TV/LCD/DVI) is silently
  unpopulated** on kernels where `struct acpi_device` no longer exposes its
  own child list — the replacement enumeration API is `EXPORT_SYMBOL_GPL` and
  unusable from this proprietary module. ACPI event handling otherwise works;
  only this one piece of hybrid-display detection degrades.
- **96xx/71xx** (siblings on the same installer generation) got the same
  `kernel/0001` kbuild `M=` fix opportunistically, and later a shared
  `select_makefile`/`PATCHLEVEL` misdetection fix too (their own `kernel/0002`)
  — both now reach real compilation, surfacing the same general class of API
  breaks 173xx had, but the actual forward-port work has not been attempted
  for either.
