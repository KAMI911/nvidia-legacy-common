# 96.43.23 → modern kernel — forward-port status

**Status: build-verified.** `nvidia.ko` compiles clean (zero errors) via
`patches/96xx/kernel/0001`-`0004` on:
- Ubuntu 20.04/kernel 5.4.0-200-generic (amd64)
- Ubuntu 24.04/kernel 6.8.0-139-generic (amd64)
- Debian trixie/kernel 6.12.107 (amd64, gcc 14.2.0) — the actual `kernel_max` target
- Debian bookworm/kernel 6.1.0-53-686-pae (**i386**)

`kernel/0004` closed the two gaps noted below as of `kernel/0003`: it fixed a
Debian split-kernel-headers-package incompatibility and a GCC 14
default-warning promotion that broke essentially all of `kernel/0003`'s
conftest.sh probes on Debian/gcc-14 — the exact same two root causes 173xx's
own `kernel/0004` found and fixed, ported directly once confirmed applicable.
See `patches/96xx/PROVENANCE.toml`'s `kernel/0004` entry for the full detail.
Not yet runtime-tested on real hardware.

**Target:** compile-clean against Linux 6.12 LTS (amd64 + i386), runtime-validated
later on real NV1x/NV2x (GeForce 2/3/4 Ti) hardware.
**Reference:** 173xx's own forward-port (`docs/forward-port-status/173xx.md`,
`patches/173xx/PROVENANCE.toml`) was the direct template for most of this
series' `kernel/0003`/`kernel/0004` fixes — same general vintage and file

## API breaks found and fixed (kernel/0003)

Full detail, including *why* each conftest probe is written the way it is,
lives in `patches/96xx/PROVENANCE.toml`'s entry for
`kernel/0003-modern-kernel-forward-port.patch`. Summary:

- ACPI headers consolidated onto `<linux/acpi.h>`
- `<asm/kmap_types.h>`, `<asm/special_insns.h>`, `<asm/set_memory.h>` presence probes (arch/x86-local headers, invisible to the existing header-prefix probe)
- `mtrr_add`/`mtrr_del` unexported on out-of-tree modules (link-time only, invisible at compile time) → `arch_phys_wc_add`/`arch_phys_wc_del`, with handle tracking threaded through `os-agp.c` and `os-interface.c`'s write-combining paths
- `smp_call_function`/`on_each_cpu` int→void return
- `spin_unlock_wait()` removed → lock/unlock pair fallback
- `struct file.f_dentry` removed → `f_path.dentry`
- `register_cpu_notifier`/CPU-hotplug-notifier API removed (guards `nv_kern_cpu_callback` and both hotcpu-notifier call sites)
- `ioremap_nocache` removed → `ioremap`
- `__vmalloc()` lost its `pgprot_t` argument (Linux 5.8)
- `vma->vm_flags` became read-only (Linux 6.3+) → `vm_flags_set()`, 5 call sites
- `i2c_del_adapter()` became void-returning
- `create_proc_entry()`-era procfs API fully removed → bridged via a `read_proc_t`-shaped shim (`nv_proc_shim_t`/`nv_proc_shim_show`/`nv_create_proc_read_entry`) so every original `nv_kern_read_*()` body is unchanged
- `init_timer()`/`timer_setup()` (Linux 4.15+, exact pattern from 304xx's `0004-timer-4.15.patch`)
- `do_gettimeofday()`/`struct timeval` removed (Linux 5.0+) → `timespec64`/`ktime_get_real_ts64()`, exact pattern from 173xx's `0002-timespec64` patch
- `num_physpages` global removed → `get_num_physpages()`
- CR4 register-move asm bug: an explicit 32-bit `movl` suffix on a control-register move is rejected by newer assemblers in 64-bit mode (control-register moves are always native-width regardless of suffix) → plain unsuffixed `mov` with `unsigned long`-typed operands
- `__flush_tlb()` (kernel-internal, no longer available to modules) → open-coded CR3 reload (`NV_FLUSH_TLB()`), exact pattern from 173xx
- `current->state` direct assignment → `set_current_state()`
- `CORE_OBJS` (nv-kernel.o blob) needed routing through Kbuild's `if_changed` so modpost can find a `.cmd` file for it, exact pattern from 173xx's `kernel/0003`
- `tasklet_disable()` → open-coded busy-wait against the public `TASKLET_STATE_RUN` bit (`NV_TASKLET_DISABLE()`), because `tasklet_unlock_wait()` became `EXPORT_SYMBOL_GPL` on later kernels and this proprietary-licensed module can't call it directly (a modpost link failure, not a compile error)

## Debian split-headers + gcc14 (kernel/0004)

- Debian's per-flavor kernel-headers package is a slim shim (`include/{config,generated}` + `arch/*/include/generated` only) whose own Makefile is `include /path/to/...-common/Makefile`; the real `linux/*.h`/`uapi/*.h`/`arch/*/include/asm/*.h` etc. live in the sibling `-common` package. conftest.sh's hand-rolled `-I`/`-include` paths (rooted at `$HEADERS`) don't follow that chain the way real kbuild does. Fixed by detecting the common-package root (parsing the flavor Makefile's one `include` line) and adding it everywhere: `test_headers()`, `select_makefile`'s own `linux/version.h` check, `build_cflags()` (`-I.../include`, `-I.../include/uapi`, `-I.../arch/x86/include` — `<asm-generic/types.h>`, pulled in transitively, lives under the common package's `include/uapi/`), and `kernel_patch_level`'s `VERSION`/`PATCHLEVEL` detection (the flavor stub Makefile has neither; falls back to the common package's real Makefile).
- GCC 14 promoted `-Wimplicit-function-declaration`/`-Wimplicit-int`/`-Wint-conversion` to hard errors by default, breaking every wrong-argument-count/implicit-declaration conftest probe (`kernel/0003` added several) uniformly. Fixed with explicit `-Wno-error=` flags in conftest.sh's own `BASE_CFLAGS` — real kbuild-driven compilation is unaffected, since kbuild always passes `-Werror=implicit-function-declaration` explicitly regardless of gcc's default.
- `nv-vm.c`'s `sg_ptr->page_link = virt_to_page(base)` is an implicit pointer-to-integer assignment, a hard error under gcc 14's `-Wint-conversion`-as-error default (outside any conftest probe) → explicit `(unsigned long)` cast, exact fix from 173xx's `0004`.
- 96xx's CR4 code (fixed as part of `kernel/0003`) already uses a `NVCPU_X86_64`-unconditional raw-asm `mov`, not the `__write_cr4()`/`__read_cr4()` wrapper functions 173xx's `0004` also had to re-guard for i386 (those call an unexported `native_write_cr4()`/`native_read_cr4()` on i386) — so that part of 173xx's fix doesn't apply to 96xx.
